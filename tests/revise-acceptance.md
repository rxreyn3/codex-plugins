# Revise acceptance scenarios

Run in a disposable project with the exact installed development skill path. These are behavioral checks; the Node.js suite and skill validators only verify source contracts and packaging. Preserve before/after artifacts and identify the candidate commit and installed version in the trial record.

## Initial Plan materialization

Prepare a ready design and an initial `in-review` plan whose `parent` names that design. The plan has never been ready and has no `materialized_at` or `design_fingerprint`. Include three candidate phases: screen layout, public conversation startup, and cleanup. Current source implements none of them.

Ask Revise to replace public startup with backend-issued private tokens. Expect one pre-transfer proposal naming the exact design and candidate plan, corresponding responsibilities and criteria, and preserved unaffected material. After approval and review, both artifacts agree because authority has not transferred yet. No sibling plan or product source changes.

Complete initial Plan review. Immediately before readiness, change the design in the fixture and confirm Plan stops rather than recording a stale fingerprint. Restore the approved design, resume, and confirm the ready plan records `materialized_at`, `design_fingerprint: git-blob:<hash>`, and a compact `## Accepted Design Decisions`. The design remains byte-identical during the transfer.

## Transferred Plan architectural revision

Use a fresh fixture whose ready plan records a design fingerprint and whose implementation has begun. The frozen design specifies public startup; the current Plan and source implement private-token startup after a dated amendment. Keep completed layout and cleanup checks plus a superseded sibling plan.

Invoke Revise with the ready Plan and request an interface change affecting startup and its later acceptance. Do not mention the frozen Design in the prompt.

Observe and approve the revision:

- Revise reads and edits the Plan as the sole live specification. The Design and sibling plan remain byte-identical; historical disagreement with Design is not treated as drift or synchronized.
- The proposal names the recorded fingerprint, current Plan sections, preserved progress, and invalidated checks. It states that frozen rationale was not consulted.
- The result appends a compact Decision Amendment with old intent, new intent, rationale and evidence, affected phases, and reopened checks. It updates affected current Plan sections rather than relying on the amendment alone.
- Independent affected review runs before the Plan returns to ready. Current source remains evidence rather than being described as already satisfying the new interface.

Repeat with a request whose answer depends on a rejected alternative recorded only in Design. Revise may read only the relevant Design decision/context sections, must disclose that use, and still must leave Design byte-identical. Reading the complete Design without a demonstrated need fails this scenario.

## Transferred Plan execution-only revision

On a separate copy, correct an unavailable executable from `python` to verified `python3` without changing intended outcomes. Expect a Plan-only proposal covering every equivalent current occurrence. The Design and source remain byte-identical, valid completion survives, and Revise appends a Follow-up without a Decision Amendment or architectural review.

## Current evidence consistency

Use a mature transferred Plan whose current overview says startup still uses `agentId`, while later dated evidence and source establish private-token startup. Request a related diagnostic verification change without identifying the stale overview.

The proposal must include the affected current-summary correction. Current prose must distinguish implemented startup, recorded observations, and unproven diagnostic acceptance. Valid implementation checks survive; expanded acceptance stays unchecked. Frozen Design differences are historical provenance and are neither audited nor disclosed as an unresolved current contradiction.

## Design input routing

Invoke the same architectural feedback with a Design path under these separate fixtures:

- No child plan: revise Design alone and recommend Plan when ready.
- One initial `in-progress` or `in-review` child that has never been ready: select the pre-transfer pair.
- One transferred active child plus an explicitly superseded sibling: route to the active Plan and keep Design byte-identical.
- Two plausible active children or unclear legacy transfer evidence: ask for path selection; timestamps alone must not decide.

A later Plan temporarily marked `in-review` but carrying materialization metadata remains transferred. It must not reactivate Design authority.

## Fundamental rethink

Request a phase-local architectural change affecting two phases. Expect an ordinary transferred-Plan Decision Amendment, not a new Design merely because the change is architectural.

On a fresh fixture, request a new feature goal that reopens unresolved architecture and invalidates the existing decomposition. Expect Revise to explain the boundary and recommend a successor Design followed by a successor Plan. It must not mutate the frozen pair or start Design automatically.

## Review and interruption boundaries

When independent revision review cannot run for a material transferred-Plan change, expect the Plan to remain `in-review` with explicit pending review. A changed live artifact between proposal and approval must be reconciled before writing. Existing review rows stay unresolved unless the approved, reviewed change addresses them. A Design `--resume` must route unfinished pre-transfer revision work back to Revise rather than finalizing from old slice approvals.

## Discovery from Design and Plan

Ask Design to revise approved architecture after a transferred plan exists, or raise architectural feedback after initial Plan readiness. Expect one concrete Revise handoff naming the Plan. There must be no frozen-Design edit, pair synchronization, automatic stage invocation, or replacement plan that discards implementation progress.
