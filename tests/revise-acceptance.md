Prepare a ready design and a ready plan whose `parent` names that design. Include three completed phases: screen layout, public conversation startup, and cleanup. Include a later checked Start/Stop/Start acceptance result. Keep an explicitly superseded sibling plan. Current source should implement public startup and cleanup and expose a backend membership check and a private-token provider interface as evidence.

Invoke:

```text

```

Observe a single proposal naming the exact design and active plan, source-backed backend/client responsibilities, corresponding payloads and criteria, and specific progress invalidation. Approve that proposal, then inspect the artifacts:

- Both current documents express the same intended flow; live source is still accurately described as public startup.
- Unrelated layout and unchanged cleanup implementation remain checked. Changed startup work and dependent acceptance reopen with reasons.
- Phase files/dependencies remain complete, including unrelated metadata fields.
- Old decisions and verification records remain dated history; the main sections are current.
- Independent affected review runs before readiness. No sibling plan or product source changes.

## Design entry and ambiguous active plan

Invoke the architectural request with the design path. With one active child and one explicitly superseded child, expect selection of the active child and one coordinated proposal. With two plausible active children, expect a path-selection question before writing; timestamps alone must not decide. After selecting one, only that plan and its design may change. A supplied historical plan or conflicting parent link also requires resolution.

## No active plan and legacy plans

With no active child, a design revision updates only the design and recommends Plan when ready. Pending, unapproved slices remain pending. A standalone plan without a design parent retains the existing plan-only revision path; it must not create a design. A declared but missing design parent is an unresolved link, not a standalone plan.

## Review and interruption boundaries

When independent revision review cannot run, expect explicit pending review and no ready-pair claim. A Design `--resume` must route an unfinished revision back to Revise rather than finalizing from old slice approvals. Existing review rows stay unresolved unless the approved, reviewed change actually addresses them. A changed artifact between proposal and approval must be reconciled before writing; a partial pair write must be reported and resumed from the persisted proposal, without erasing concurrent edits.

## Discovery from Design and Plan

Ask Design to revise approved architecture after a plan exists, or raise an architectural finding during Plan review. Expect a single concrete Revise handoff. There must be no plan-local tactical override of a stale design, automatic stage invocation, or replacement plan that discards implementation progress.
