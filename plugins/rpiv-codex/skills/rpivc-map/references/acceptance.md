# Map acceptance

Record the companion digest, rendered digest, source revisions, browser/environment, review evidence and limitations. Use candidate output until all applicable checks pass. These checks establish map behavior, not product deployment or successful provider operations.

## Entry behavior

For entry-instruction changes, run a bounded scenario evaluation using the final skill text. Capture actual first responses and, where useful, a follow-up choice; inspect behavior rather than matching phrases. Keep evaluation output outside tracked skill files and distinguish simulated responses from a full fresh-chat mapping run.

- Bare invocation with one clear subject: offer two or three grounded views, recommended first, with a custom-answer escape hatch; stop before creating output.
- Multiple plausible subjects: ask subject first without mixing view choices. With no artifacts or context, ask for a bounded topic instead of surveying the repository.
- Explicit subject and visual goal: proceed without a redundant menu. A letter or custom view selection should lead to work, not a setup wizard.
- Saved approved map plus newer failed candidate: a different snapshot view preserves its evidence date; a change comparison uses the approved baseline and affected current evidence.
- Conflicting ownership: preserve the conflict and ask only what is needed before claiming authoritative intent. A newer file or selected view cannot settle authority or approve proposed scope.

## Data and authority

- Validate identifiers, endpoints, source references, independent claim dimensions and every generated section's parity with the companion.
- Check unresolved scope stays unresolved; settled outcomes stay agreed despite unfinished design/build/checks. Reference code, ticket relationships and Done labels do not establish scope or runtime behavior.
- Exercise one map across Explore, Research, Design, Plan and the alternative Blueprint route. Preserve identity; record owner changes and pending checkpoints. A Plan that once reached ready stays owner during revision. Generated plan code does not become implementation evidence.
- Compare to the exact last approved revision. Exercise first-map, meaningful change, no-change and unavailable-source cases. Reject a mismatched baseline and verify a failed candidate does not replace the approved result. A changed design must not upgrade implementation/check claims automatically.
- Preserve prior decisions and stable component identities. Document justified removals or changed relationships. Recommendations require feasibility and consequence evidence; suggestions need dependency evidence. Do not accept an invented recommendation just to populate the screen.

## Browser and wording

- Read a normal and failure journey. Verify directions, endpoints, line-style legend and numbered list match; no false joins, crossed unrelated parts, clipped labels or duplicate initialization.
- Choose a ticket, inspect a direct part and an outside dependency, then a connection and question. Keep ticket, journey and visible connection context. Explain the specific ticket portion and each outside dependency without transferring scope.
- Use the explicit connected action and return. Check the prior context restores. Repeat from the mobile picker.
- Discover every open question from Review remaining questions without opening each component. Check deduplication, next-action groups, no artificial user choice and selected question focus/scroll with unrelated disclosures closed.
- Inspect every connection by keyboard and touch. Payload, trigger and evidence or explicit unknowns must be available, with access to endpoint parts.
- Review every question: agreed behavior, unresolved work, concrete consequence, illustrative example where needed, and actionable next step. Expand candidates/evidence; verify unsupported technical recommendations stay unset and clicks save no decisions.
- Keep Still to decide separate from Agreed work remaining. Existing behavior and unchanged constraints are not unfinished tasks. Independent agreement/implementation/check evidence appears together only in selected detail.
- On narrow mobile, grouped picker precedes detail. Select a journey, inspect one part, use Choose another part, inspect a second, and verify useful focus/scroll and preserved context. Check overflow and text clipping.
- Inspect desktop and mobile in light and dark appearances. Review screenshots and interactive behavior; a successful screenshot command alone is not visual inspection.
- Open Since the last refresh and visit affected parts without losing context. Check meaningful source-backed wording and honest coverage gaps. Follow an answered question from the refresh summary: open its Recorded decisions section and selected explanation, with useful focus and the same journey/ticket.

## Worked examples for skill changes

Use Voice and one smaller unrelated system; keep example facts separate from generic code. Voice must preserve all six supplied acceptance cases: agreed provider/Alan deletion despite open design; separate deletion outcomes; existing privacy handling/manual interim versus future tooling; unchanged Support-summary treatment; design progress without implementation claims; related evidence without invented approval. A historical snapshot is not a current provider check. Do not publish private evidence in the plugin repository; keep private worked output outside tracked files.

Use a small synthetic example with its own explicitly fictional source artifact for portable regression tests. Show a simpler flow. Do not cite a synthetic scenario as production evidence.

## Final review and hosting

Have Codex Advisor inspect the final data, wording and actual rendered desktop/mobile views. Record review findings, resolutions and exact digests before promoting the candidate. Any subsequent factual or visual edit needs review of the changed result. Approval cannot be inferred from silence, prior proposal approval or automated checks.

When hosting is requested, verify existing audience and identity before publishing. Preserve sandbox and both content security policies for an embedded export; do not weaken them to make rendering work. Report local checks, deployment and authenticated inspection separately.
